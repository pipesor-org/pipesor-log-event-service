## First evidence registration increment

Baseline: Log/Event `d1f0277`, source model `505232c`, NLP `1d6e54f`.
The local owner uses UUIDv5 in the URL namespace for
`urn:pipesor:v1:evidence:<message_id>`, matching NLP's existing derivation.
This is an implementation choice for this increment. The event producer,
transport and authorization agreements remain under PD-031/033/034.

The internal registration boundary takes already protected and minimized
evidence. The injected authority checks caller access and committed operational
membership. Each authority must be bound to the authenticated caller and
the operation, including permission to inspect the exact evidence ID before
any lookup. PostgreSQL commits a new item once. A matching re-delivery returns
the same ID. Changed persisted fields under that ID produce a conflict.
Comparison reflects the stored projection and microsecond precision.
Validation checks authority before reading the Log/Event store and returns
membership only. The application returns no excerpt or summary from that
operation. Recorded time has the PostgreSQL microsecond precision of the
current model. Live authority must come from the agreed owner integration.

Acceptance: match the producer UUID test vector, prove exact replay and
conflicting payloads on actual PostgreSQL, exercise a concurrent replay, and
distinguish missing from crossed references only for an authorized caller.
Migration V1 creates the Log/Event evidence table and its stage type from the
model. It uses logical references to Pipeline identities. PostgreSQL stores
the minimized representation; GitHub remains the source for complete logs.

The isolated intake reads Ingestion's `protected_workflow_evidence` v2 and
checks the delivery metadata against the body. It derives the logical
references and gives an explicitly provided authority the capture scope,
GitHub identities, commit, both source timestamps and the validated
correlation ID before registration and on every replay.
This local projection uses `occurred_at` for `observed_at` at PostgreSQL
microsecond precision. The authority receives both timestamps at the original
precision. JDBC replay compares the persisted projection. The owner
authority, broker settlement, public queries, grants, runtime limits and
retention operations depend on their own contracts.

## GitHub enforcement limitation

The baseline audit confirmed private visibility, `main` as default branch and squash-only merge settings. The GitHub rulesets API returned HTTP 403 with a plan-upgrade requirement for this service; no enforced branch protection or independent approval gate is certified. PR-title/body squash formatting and automatic branch deletion were historical initialization settings, not independently revalidated by this audit. Mandatory reviewed PRs and no direct pushes to main remain contribution rules; server-side enforcement has not been established. Keep these repositories private; do not change visibility to work around that limitation. No empty CI checks or deployment workflows are added.

## Scoped Correlation membership

The approved membership increment freezes capture tenant, GitHub installation
and scope revision when protected v2 evidence is registered. The owner keeps
the original scope on replay. A changed scope under the same evidence ID is a
conflict. The scope tuple records historical provenance. Current permission
still comes from an authenticated authority.

The Correlation membership operation uses the scoped handler. Its SQL filter
requires the evidence ID, all three scope values, execution and incident to
match before source comparison. A missing, crossed or legacy unbound row has
the same not-ready result. Source contradiction is distinguishable only after
that filter matches. The endpoint composition must authorize the dedicated
Correlation principal and scope before lookup.

V2 adds nullable scope columns with an all-null or complete-valid constraint.
Existing V1 rows stay unbound and cannot gain scope from a registration replay.
They require separately approved reconciliation before scoped membership.

## MVP runtime composition

The service runs as one Spring Boot image with profiles `local` and `azure`
(pipesor-docs ADR-022, platform identity contract v1, runtime manifest).
Service Bus subscription `log-event` feeds `ProtectedEvidenceIntake`; the
source authority is Pipeline's operational-reference check, called with a
workload token (`pipeline`, `Evidence.Check`). Its port
(`application/ports/OperationalReferenceAuthority`, with `ExecutionBinding`)
lives in the application layer; the HTTP adapter lives in infrastructure.
`NOT_READY` and unavailable decisions are abandoned for redelivery because
Pipeline may not have applied the execution snapshot yet; permanent contract
failures are dead-lettered. The membership route is a Spring MVC controller
behind the platform decoder and accepts only `correlation` with
`Correlation.EvidenceMembership.Check`. The tenant is the environment tenant;
the installation is not pinned because the scoped lookup already filters by
the requested installation and revision. Protected evidence 2.2 locators are
validated by shape only (protected-evidence-v2.2.md); 2.1 keeps its exact rules.
Log/Event has no human API in the MVP (mvp-http-api-v1.md).
