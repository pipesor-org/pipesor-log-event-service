# Repository instructions

## Context by task

- Before implementation, read the [common backend conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/backend-conventions.md) and [Java/Spring conventions](https://github.com/pipesor-org/pipesor-docs/blob/main/docs/development/java-spring-conventions.md). Use the accessible pipesor-docs checkout when available, distinguishing local changes from integrated main. Apply only the conventions relevant to this service; they do not add tables, integrations or permissions.
- Use [README.md](README.md#development-and-verification) for setup, runnable commands and contribution policies. Add verified commands there when introducing application tooling; reference them rather than maintaining a second command list here.
- For event consumption, evidence queries or persistence changes, consult [architecture](docs/architecture.md#service-relationships) and its current architecture/domain sources. For original-log references or storage changes, apply ADR-019 as linked in the current MVP alignment. Follow the references for the affected subject, not the entire documentation set for every edit.
- For dependency selection, runtime configuration, migrations or delivery work, consult the relevant sections of the [deployment contract](docs/deployment-contract.md). Its development baseline records the authorized version-selection policy; its data lifecycle records table ownership and retention limits.
- Treat local architecture summaries as navigation, not frozen specifications. Use the accessible `../../pipesor-docs/` checkout or linked sources on `main`, accounting for later accepted decisions and relevant uncommitted changes. Inspect uncommitted source changes separately; their presence does not establish integration or approval. Report unavailable or conflicting evidence when it affects the task. Documentation links must follow `main` across repositories and relative paths within this repository; a consulted revision may be recorded as text only.

## Implementation constraints

- Confine persistence changes to owned evidence data. Sharing the `evidence` schema does not authorize writes to `correlated_contexts`; preserve logical incident/execution references without adding cross-schema foreign keys or cross-context ORM navigation. Check event consumption, persistence and query behavior together when changing evidence registration.
- Store sanitized evidence, metadata and excerpts under the current model. Do not restore workload Blob, its removed columns or complete-log duplication to fill a retrieval gap. Preserve evidence identity, provenance and `correlationId`; do not invent a replacement locator or direct integration absent from the agreed contracts.
- Check authorization for evidence queries and reference resolution, including access to evidence from another pipeline or execution. Do not infer access from possession of an evidence ID, a reference or provisional grants. Keep sensitive payloads out of responses and diagnostic logs.
- Use the agreed event and reference-validation contracts for duplicate, delayed or independently arriving data. Do not assume delivery order, exactly-once processing or availability of referenced workflow context. GitHub log availability does not establish independent recovery or compliance with the documented retention policy; do not introduce purge behavior or guarantees while those mechanisms remain unresolved.
- A request to implement a local increment authorizes its required local code, tooling and checks. Do not create cloud resources, permissions or secrets, or modify neighboring repositories as a side effect. Keep credentials and sensitive evidence out of committed files and reported output.
- If event/API semantics, authorization, original-log retrieval or retention requirements needed by the increment are unresolved, identify the specific pending decision and its impact. Continue independent work; do not invent integration behavior or block the whole service because an unrelated decision remains open.

## Verification and handoff

Use the applicable checks documented in the README. Add behavior checks with the first executable increment, including material failure cases for duplicate delivery, missing logical references, unauthorized queries and sensitive-data exposure. Use synthetic evidence and isolated fixtures; live database, GitHub or Azure checks need their own agreed scope and access.

For documentation-only edits, check affected links and source coherence; parse TOML when changing agent configuration. Do not claim a build or integration passed before it exists and has run. Keep the documentation that owns a changed behavior or command current in the same change. Report what changed, checks actually performed and remaining blockers. For substantial work spanning sessions, keep a task-specific plan with scope, acceptance criteria and verification progress; a small edit needs no plan file.

When a focused review is warranted and delegation is authorized, `evidence_reviewer` checks evidence ownership, provenance, access, retention assumptions and event delivery. Supply the task and affected paths. Its review supplements the main agent's verification and human review.
